# Documentation audience

All articles in this directory are user-facing guides for FS PBX users and administrators.

- Write around the reader's task: what the feature does, where to find it, what to enter, and how to apply the change.
- Include supported features and limitations in plain language when they affect the reader's choices.
- Include technical names or values only when the reader must enter them in the product or needs them to make a configuration decision.
- Keep implementation details, database and template mechanics, internal fallback rules, investigation history, test results, packet traces, observed timings, and engineering diagnostics out of articles. Keep that evidence in the working conversation or development notes.
- Do not turn each discovery during development or troubleshooting into a documentation paragraph. Routine user troubleshooting belongs only where it helps complete the documented task.
- Before finishing, review each paragraph from the user's perspective: if it does not help them understand, configure, or use the feature, remove it.
